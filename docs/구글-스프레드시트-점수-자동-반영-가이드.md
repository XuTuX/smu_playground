# 구글 스프레드시트 점수 자동 반영 가이드

## 1. 문서 목적

이 문서는 SMU 놀이터 운영자가 구글 스프레드시트에 점수를 입력하거나 수정하면 웹사이트의 개인 랭킹, 학과 랭킹, 최근 기록에 자동으로 반영되도록 만드는 방법을 설명한다.

현재 프로젝트는 `lib/mock-store.ts`의 서버 메모리에 점수와 게임 세션을 저장한다. 이 방식은 로컬 시연에는 편하지만 서버가 재시작되거나 새로 배포되면 실행 중 추가된 데이터가 사라질 수 있다. 구글 스프레드시트를 확정 점수의 원장으로 사용하면 운영자가 익숙한 화면에서 데이터를 관리할 수 있고, 서버 재시작 뒤에도 점수를 다시 읽을 수 있다.

이 문서의 권장안은 다음과 같다.

- 확정된 점수는 구글 스프레드시트의 `점수` 시트에 보관한다.
- 웹사이트는 Google Sheets API를 통해 시트를 서버에서만 읽는다.
- 홈페이지는 현재처럼 5초 간격으로 `/api/dashboard`를 호출한다.
- 서버는 시트 데이터를 5초 정도 캐시하여 Google API 호출량을 제한한다.
- 관리자 직접 입력과 현장 게임 등록도 최종적으로 같은 시트에 행을 추가한다.
- 잘못 입력한 행은 삭제하는 대신 `active`를 `FALSE`로 바꿔 제외한다.

> 구글 스프레드시트는 이 행사처럼 비교적 작은 규모의 운영 도구에는 적합하지만, 동시 쓰기가 매우 많거나 엄격한 트랜잭션이 필요해지면 PostgreSQL 같은 데이터베이스로 이전하는 것이 안전하다.

## 2. 완성 후 동작 흐름

```text
운영자가 구글 스프레드시트에 점수 입력
                    │
                    ▼
          비공개 Google Sheets API
                    │
                    ▼
       Next.js 서버가 점수 읽기·검증·정규화
                    │
                    ├── 잘못된 행은 제외하고 관리자 화면에 표시
                    │
                    └── 정상 행만 기존 랭킹 계산 함수에 전달
                                      │
                                      ▼
           홈 / 개인 랭킹 / 학과 랭킹 / 최근 기록
```

현장 게임 점수까지 한 원장으로 관리할 때는 다음 흐름이 추가된다.

```text
ESP32 점수 도착 → 학생이 학과·닉네임 등록 → 점수 시트에 행 추가
관리자 직접 입력 ───────────────────────→ 점수 시트에 행 추가
```

구글 시트를 브라우저에서 직접 읽게 만들면 인증 정보가 노출될 수 있으므로, Google API 호출은 반드시 Next.js 서버에서만 수행한다.

## 3. 현재 프로젝트에서 바뀌는 부분

현재 점수 조회는 동기 함수인 `getAllScores()`를 사용한다. Google Sheets API는 네트워크 요청이므로 점수 조회 함수를 비동기로 바꾸어야 한다.

| 현재 파일 | 필요한 변경 |
|---|---|
| `lib/mock-store.ts` | 메모리 점수 저장소 역할을 개발용 대체 수단으로 축소 |
| `lib/google-sheets.ts` | 서비스 계정 인증, 시트 읽기·행 추가 기능 신규 작성 |
| `lib/sheet-score-parser.ts` | 행 검증, 타입 변환, 중복 제거 기능 신규 작성 |
| `lib/score-store.ts` | 실행 환경에 따라 Google Sheets 또는 mock 저장소를 선택하는 공통 계층 신규 작성 |
| `app/api/dashboard/route.ts` | 비동기로 시트 점수를 읽어 대시보드 데이터 반환 |
| `app/api/admin/scores/route.ts` | 관리자 점수를 메모리 대신 시트에 추가 |
| `app/api/sessions/[sessionId]/register/route.ts` | 학생 등록 완료 시 확정 점수를 시트에 추가 |
| `app/api/admin/snapshot/route.ts` | 마지막 동기화 시간과 오류 행 수 반환 |
| `app/page.tsx` 및 랭킹 페이지 | `await getAllScores()` 형태로 변경 |
| `components/admin/AdminConsole.tsx` | 동기화 성공·지연·실패 상태 표시 |

홈의 `components/home/HomeDashboard.tsx`는 이미 5초마다 `/api/dashboard`를 다시 요청하므로 기본 자동 갱신 구조가 준비되어 있다. 다만 `/ranking`, `/games/[gameId]`, `/departments/[departmentId]`는 현재 서버 렌더링 시 한 번만 점수를 읽으므로, 해당 화면을 열어 둔 상태에서도 자동 갱신하려면 별도의 클라이언트 polling을 추가해야 한다. 그렇지 않으면 새로고침할 때 최신 값이 표시된다.

## 4. 권장 스프레드시트 구성

하나의 구글 스프레드시트에 다음 세 개의 시트를 만든다.

1. `점수`: 실제 점수 원장
2. `코드표`: 게임 ID와 학과 ID 확인용 목록
3. `입력안내`: 운영 규칙과 예시

### 4.1 `점수` 시트 열 구성

첫 번째 행은 아래의 영문 필드명을 정확히 사용한다. 코드는 열 위치보다 헤더 이름을 기준으로 읽게 만들면 추후 열 순서를 바꿔도 안전하다.

| 열 | 필드명 | 필수 여부 | 예시 | 설명 |
|---:|---|---|---|---|
| A | `record_id` | 필수 | `manual-20260827-0001` | 각 행을 구분하는 고유 ID |
| B | `session_id` | 권장 | `3c5e...` | ESP32 세션 또는 관리자 입력 세션 ID |
| C | `student_id` | 관리자 입력 시 필수 | `20261234` | 학번. 현장 화면에서 받지 않으면 빈칸 허용 |
| D | `game_id` | 필수 | `flappy` | 프로젝트에서 사용하는 게임 ID |
| E | `department_id` | 필수 | `ai-computer` | 프로젝트에서 사용하는 학과 ID |
| F | `nickname` | 필수 | `세명왕` | 2~12자 닉네임 |
| G | `score` | 필수 | `128` | 0~999 정수 |
| H | `created_at` | 필수 | `2026-08-27T14:30:00+09:00` | ISO 8601 형식의 등록 시각 |
| I | `active` | 필수 | `TRUE` | `FALSE`이면 랭킹에서 제외 |
| J | `source` | 권장 | `sheet` | `sheet`, `admin`, `esp32` 중 하나 |

예시 데이터는 다음과 같다.

| record_id | session_id | student_id | game_id | department_id | nickname | score | created_at | active | source |
|---|---|---|---|---|---|---:|---|---|---|
| manual-20260827-0001 | manual-20260827-0001 | 20261234 | flappy | ai-computer | 세명왕 | 128 | 2026-08-27T14:30:00+09:00 | TRUE | sheet |
| esp32-a1b2c3 | esp32-a1b2c3 |  | reaction | nursing | 번개손 | 214 | 2026-08-27T14:31:12+09:00 | TRUE | esp32 |

### 4.2 게임 ID

현재 프로젝트에서 허용하는 값은 다음과 같다.

| 게임명 | `game_id` | 점수 범위 |
|---|---|---:|
| 1D FLAPPY | `flappy` | 0~999 |
| REACTION | `reaction` | 0~999 |
| DINO RUN | `dino-run` | 0~999 |
| TIMING | `timing` | 0~999 |
| RHYTHM | `rhythm` | 0~999 |

학과 ID는 `data/departments.ts`의 `id` 값을 사용한다. 운영자가 오타를 내지 않도록 `코드표` 시트에 게임과 학과 목록을 넣고, `점수` 시트의 `game_id`와 `department_id` 열에 드롭다운 데이터 검증을 설정하는 것이 좋다.

### 4.3 시트 운영 규칙

- 첫 번째 헤더 행은 수정하거나 삭제하지 않는다.
- 점수는 문자열이 아니라 숫자로 입력한다.
- 학번은 앞자리 `0`이 필요한 경우를 대비해 텍스트 형식으로 지정한다.
- 잘못된 기록은 행 삭제보다 `active=FALSE`로 비활성화한다.
- `record_id`는 반드시 중복되지 않게 한다. 값이 있는 `session_id`도 중복되지 않게 한다.
- `created_at`을 비워 두었을 때 자동으로 현재 시각을 넣을지, 오류로 처리할지는 구현 전에 한 가지 정책으로 고정한다. 권장 정책은 오류 처리이다.
- 수식이 들어간 점수는 표시값이 아닌 계산된 숫자값으로 읽도록 설정한다.
- 시트 공유 권한은 행사 운영자와 서비스 계정으로 제한한다.

## 5. 중복 점수 처리 정책

현재 관리자 직접 입력은 같은 `학번 + 게임` 조합에서 최고 점수 하나만 반영한다. 구글 시트에서도 이 규칙을 유지한다.

권장 방식은 기존 행을 덮어쓰지 않고 모든 시도를 행으로 남긴 뒤, 서버가 랭킹 계산 전에 최고 점수만 선택하는 것이다.

```text
20261234 + flappy + 100점
20261234 + flappy + 130점  → 130점만 랭킹 반영
20261234 + flappy + 120점
```

이 방식의 장점은 다음과 같다.

- 누가 어떤 점수를 입력했는지 기록을 보존할 수 있다.
- 동시에 입력해도 기존 셀을 덮어쓰는 충돌이 적다.
- 운영 중 정정 이력을 확인할 수 있다.

현장 등록 화면은 현재 학번을 받지 않으므로 `student_id`가 없는 ESP32 기록은 `record_id` 또는 `session_id` 단위의 독립 기록으로 처리한다. 현장 점수도 학생별 최고 기록만 인정해야 한다면 등록 화면에 학번 입력 필드를 추가해야 한다.

중복 처리 순서는 다음과 같이 잡는다.

1. `active=FALSE` 행 제외
2. 형식이 잘못된 행 제외
3. 같은 `record_id`의 중복 행과, 비어 있지 않은 동일 `session_id`의 중복 행 제거
4. `student_id`가 있는 행은 같은 `student_id + game_id` 중 최고 점수만 유지
5. 최고 점수가 같으면 `created_at`이 빠른 기록 유지
6. 정리된 결과를 기존 `getDepartmentStandings()`와 `getPlayerStandings()`에 전달

## 6. Google Cloud와 서비스 계정 설정

### 6.1 프로젝트와 API 준비

1. [Google Cloud Console](https://console.cloud.google.com/)에서 새 프로젝트를 만들거나 기존 프로젝트를 선택한다.
2. API 및 서비스 메뉴에서 **Google Sheets API**를 활성화한다.
3. IAM 및 관리자 → 서비스 계정으로 이동한다.
4. `smu-playground-sheets` 같은 이름으로 서비스 계정을 만든다.
5. 로컬 또는 일반 호스팅 환경에서 사용할 경우 JSON 키를 한 번 생성한다.
6. JSON 파일의 `client_email`과 `private_key` 값을 안전한 비밀 저장소에 보관한다.

서비스 계정 키는 비밀번호와 같은 비밀 정보다. 저장소에 JSON 파일을 커밋하지 말고, 유출이 의심되면 즉시 키를 비활성화·교체한다. 가능하면 배포 플랫폼이 지원하는 짧은 수명의 자격 증명이나 Workload Identity Federation을 사용하는 것이 더 안전하다.

### 6.2 스프레드시트 공유

1. 사용할 구글 스프레드시트를 연다.
2. 우측 상단 **공유** 버튼을 누른다.
3. 서비스 계정의 `client_email` 주소를 추가한다.
4. 사이트가 시트를 읽기만 하면 **뷰어**, 관리자·ESP32 결과까지 시트에 추가하면 **편집자** 권한을 준다.
5. “링크가 있는 모든 사용자” 공개 설정은 사용하지 않는다.

### 6.3 스프레드시트 ID 확인

시트 URL이 다음과 같다면:

```text
https://docs.google.com/spreadsheets/d/1AbCdEfGhIjKlMnOpQrStUvWxYz/edit#gid=0
```

`/d/`와 `/edit` 사이의 값이 스프레드시트 ID다.

```text
1AbCdEfGhIjKlMnOpQrStUvWxYz
```

## 7. 환경 변수 설정

프로젝트 루트의 `.env.local`에 다음 값을 추가한다.

```dotenv
GOOGLE_SHEETS_SPREADSHEET_ID=1AbCdEfGhIjKlMnOpQrStUvWxYz
GOOGLE_SHEETS_SCORE_RANGE="'점수'!A1:J"
GOOGLE_SERVICE_ACCOUNT_EMAIL=smu-playground-sheets@example-project.iam.gserviceaccount.com
GOOGLE_SERVICE_ACCOUNT_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\n...\n-----END PRIVATE KEY-----\n"
GOOGLE_SHEETS_ENABLED=true
```

중요한 규칙은 다음과 같다.

- 이 변수들은 모두 서버 전용이다. `NEXT_PUBLIC_` 접두사를 붙이지 않는다.
- `.env.local`과 서비스 계정 JSON 파일을 Git에 커밋하지 않는다.
- 배포 환경에서는 Vercel 등의 프로젝트 환경 변수 화면에 같은 값을 등록한다.
- 배포 화면에 private key를 넣을 때 줄바꿈이 `\n` 문자열로 저장되면 코드에서 실제 줄바꿈으로 복구한다.
- `GOOGLE_SHEETS_ENABLED=false`이면 개발용 mock 저장소를 사용하도록 만들면 로컬 작업이 편하다.

`.env.example`에는 실제 비밀 값이 아닌 변수 이름과 설명만 추가한다.

## 8. 프로젝트 구현 방법

### 8.1 Google API 클라이언트 설치

Google이 제공하는 Node.js 클라이언트를 사용하면 JWT 생성과 인증 처리를 직접 구현하지 않아도 된다.

```bash
npm install googleapis
```

읽기 전용 단계에서는 다음 scope만 사용한다.

```text
https://www.googleapis.com/auth/spreadsheets.readonly
```

웹사이트가 시트에 행도 추가해야 한다면 다음 scope로 변경한다.

```text
https://www.googleapis.com/auth/spreadsheets
```

### 8.2 시트 연결 모듈 예시

`lib/google-sheets.ts`를 만들고 파일 맨 위에 `server-only`를 넣는다. 아래 코드는 구현 방향을 보여주는 예시다.

```ts
import "server-only";
import { google } from "googleapis";

const spreadsheetId = process.env.GOOGLE_SHEETS_SPREADSHEET_ID;
const scoreRange = process.env.GOOGLE_SHEETS_SCORE_RANGE ?? "'점수'!A1:J";

function getSheetsClient() {
  const email = process.env.GOOGLE_SERVICE_ACCOUNT_EMAIL;
  const privateKey = process.env.GOOGLE_SERVICE_ACCOUNT_PRIVATE_KEY?.replace(
    /\\n/g,
    "\n",
  );

  if (!spreadsheetId || !email || !privateKey) {
    throw new Error("Google Sheets 환경 변수가 설정되지 않았습니다.");
  }

  const auth = new google.auth.JWT({
    email,
    key: privateKey,
    scopes: ["https://www.googleapis.com/auth/spreadsheets.readonly"],
  });

  return google.sheets({ version: "v4", auth });
}

export async function readScoreRows() {
  const sheets = getSheetsClient();
  const response = await sheets.spreadsheets.values.get({
    spreadsheetId,
    range: scoreRange,
    majorDimension: "ROWS",
    valueRenderOption: "UNFORMATTED_VALUE",
    dateTimeRenderOption: "FORMATTED_STRING",
  });

  return response.data.values ?? [];
}
```

`UNFORMATTED_VALUE`를 사용하면 숫자 셀을 화면에 보이는 문자열이 아니라 계산된 원시 숫자값으로 읽을 수 있다.

### 8.3 헤더 기반 파싱

열 번호를 코드에 고정하면 운영자가 열을 옮겼을 때 데이터가 뒤섞일 수 있다. 첫 행을 헤더 맵으로 만든 뒤 각 값을 이름으로 가져오는 방식을 권장한다.

```ts
const REQUIRED_HEADERS = [
  "record_id",
  "game_id",
  "department_id",
  "nickname",
  "score",
  "created_at",
  "active",
] as const;

function makeHeaderMap(headerRow: unknown[]) {
  return new Map(
    headerRow.map((value, index) => [String(value).trim(), index]),
  );
}
```

각 행은 기존 `ScoreRecord`로 변환하기 전에 다음 항목을 검증한다.

- 필수 헤더 존재 여부
- `record_id`와 `session_id` 길이 및 중복 여부
- `game_id`가 `data/games.ts`에 존재하고 활성 상태인지
- `department_id`가 `data/departments.ts`에 존재하고 활성 상태인지
- `nickname`이 trim 후 2~12자인지
- 닉네임에 제어문자, `<`, `>`가 없는지
- `score`가 안전한 정수이며 해당 게임의 `maxScore` 이하인지
- `created_at`이 유효한 날짜인지
- `active`가 `TRUE`인지

시트 행 번호를 오류 정보에 포함하면 관리자가 바로 문제 셀을 찾을 수 있다.

```ts
type SheetRowIssue = {
  rowNumber: number;
  field: string;
  message: string;
};
```

### 8.4 공통 점수 저장소 계층

페이지가 Google Sheets 구현 세부 사항을 직접 알지 않도록 `lib/score-store.ts`를 둔다.

```ts
import "server-only";

export async function getAllScores() {
  if (process.env.GOOGLE_SHEETS_ENABLED === "true") {
    return getGoogleSheetScores();
  }

  return getMockScores();
}
```

기존 `lib/ranking.ts`의 계산 함수는 `ScoreRecord[]`만 받으므로 수정 범위를 작게 유지할 수 있다. 즉, 시트 행을 `ScoreRecord[]`로 바꾸는 경계만 새로 만들고 랭킹 공식은 그대로 재사용한다.

### 8.5 API Route 변경

현재 대시보드 API는 동기 함수로 점수를 가져온다. 다음과 같이 비동기로 변경한다.

```ts
import { getAllScores } from "@/lib/score-store";
import { getDashboardData } from "@/lib/ranking";

export const dynamic = "force-dynamic";

export async function GET() {
  const scores = await getAllScores();

  return Response.json(getDashboardData(scores), {
    headers: { "Cache-Control": "no-store" },
  });
}
```

브라우저 응답은 `no-store`로 두더라도, 서버 내부의 Google Sheets 읽기 결과는 짧게 캐시하는 것이 좋다. 이렇게 하면 사용자 수만큼 Google API 요청이 늘어나는 일을 줄일 수 있다.

### 8.6 5초 캐시 적용

현재 프로젝트는 `cacheComponents`를 켜지 않은 Next.js 16 구성이므로, Google Sheets 읽기처럼 `fetch`가 아닌 비동기 함수를 캐시할 때는 `unstable_cache`를 사용할 수 있다.

```ts
import { unstable_cache } from "next/cache";

export const getGoogleSheetScores = unstable_cache(
  async () => {
    const rows = await readScoreRows();
    return parseScoreRows(rows).scores;
  },
  ["google-sheet-scores"],
  { revalidate: 5, tags: ["google-sheet-scores"] },
);
```

관리자 입력 또는 학생 등록으로 서버가 시트에 행을 추가한 직후에는 `revalidateTag`로 캐시를 무효화한다.

```ts
import { revalidateTag } from "next/cache";

revalidateTag("google-sheet-scores", "max");
```

구글 시트에서 사람이 직접 수정한 경우에는 웹사이트가 변경 이벤트를 즉시 받지 않으므로 최대 캐시 시간과 클라이언트 polling 간격만큼 지연될 수 있다. 캐시와 홈페이지 polling을 각각 5초로 설정하면 보통 수 초 안에 반영되지만, 최악의 경우 약 10초 가까이 걸릴 수 있다.

더 빠른 즉시 반영이 꼭 필요하면 Google Apps Script의 설치형 변경 트리거가 Next.js의 보호된 동기화 API를 호출하게 만들 수 있다. 다만 인증, 재시도, 중복 호출 처리가 추가되므로 행사 초기 버전에는 5초 polling이 더 단순하고 안정적이다.

### 8.7 시트에 행 추가

관리자 입력과 학생 등록 결과까지 구글 시트에 보관하려면 `spreadsheets.values.append`를 사용한다. 이때 서비스 계정에는 편집 권한과 쓰기 scope가 필요하다.

```ts
await sheets.spreadsheets.values.append({
  spreadsheetId,
  range: "'점수'!A:J",
  valueInputOption: "RAW",
  insertDataOption: "INSERT_ROWS",
  requestBody: {
    values: [[
      score.id,
      score.sessionId,
      studentId ?? "",
      score.gameId,
      score.departmentId,
      score.nickname,
      score.score,
      score.createdAt,
      true,
      source,
    ]],
  },
});
```

행 추가 전에 입력값을 현재 `lib/validation.ts`와 같은 기준으로 검증하고, 요청마다 고유한 `record_id` 또는 `session_id`를 사용한다. 네트워크 재시도로 같은 행이 두 번 추가될 수 있으므로 조회 시 중복 제거가 반드시 필요하다.

## 9. 자동 갱신 범위

### 9.1 홈페이지

현재 홈페이지는 5초 polling이 이미 구현되어 있다. `/api/dashboard`가 구글 시트 점수를 반환하도록 바꾸면 별도 UI 변경 없이 학과 순위와 최근 기록이 자동 갱신된다.

### 9.2 개인·게임·학과 랭킹 페이지

현재 아래 페이지들은 처음 열 때 서버에서 데이터를 한 번 읽는다.

- `/ranking`
- `/games/[gameId]`
- `/departments/[departmentId]`
- `/ranking/[scoreId]`

선택지는 두 가지다.

1. 행사 운영상 새로고침으로 충분하면 서버 페이지를 그대로 유지한다.
2. 열어 둔 화면도 계속 갱신되어야 하면 홈페이지처럼 Client Component와 polling API를 추가한다.

행사장 대형 화면에는 자동 갱신이 유용하지만, 모든 일반 방문자 화면을 5초마다 갱신하면 불필요한 요청이 많아질 수 있다. 따라서 홈과 대형 랭킹 화면만 5초 polling을 적용하고, 상세 페이지는 새로고침 방식으로 두는 구성이 적절하다.

## 10. 장애와 복구 처리

구글 API가 일시적으로 느리거나 실패해도 화면 전체가 깨지지 않도록 다음 정책을 적용한다.

### 10.1 마지막 정상 데이터 유지

- 읽기에 성공하면 점수 목록과 성공 시각을 저장한다.
- 다음 읽기가 실패하면 마지막 정상 데이터를 계속 보여준다.
- 관리자 화면에 `동기화 지연`과 마지막 성공 시각을 표시한다.
- 서버 시작 후 한 번도 성공하지 못했다면 운영 환경에서는 임의 mock 점수를 보여주지 않고 오류 상태를 명확히 표시한다.

### 10.2 재시도

- `429 Too Many Requests` 또는 일시적인 `5xx` 오류는 지수 백오프로 제한적으로 재시도한다.
- 인증 오류인 `401`, `403`은 반복 재시도하지 않고 서비스 계정·공유 권한 설정을 확인한다.
- 잘못된 시트 행 하나 때문에 전체 동기화를 실패시키지 않고, 해당 행만 제외한다.

### 10.3 운영 중 잘못된 점수 수정

1. 해당 행의 `active`를 `FALSE`로 변경한다.
2. 올바른 값으로 새 행을 추가한다.
3. 홈페이지에서 반영 여부를 확인한다.
4. 관리자 화면의 오류 행 수와 마지막 동기화 시각을 확인한다.

## 11. 보안 체크리스트

- [ ] 스프레드시트를 전체 공개하지 않았다.
- [ ] 서비스 계정에는 운영에 사용하는 스프레드시트 문서만 공유했다.
- [ ] 읽기만 필요하면 뷰어 권한과 read-only scope를 사용한다.
- [ ] private key와 서비스 계정 JSON을 Git에 커밋하지 않았다.
- [ ] 모든 Google 자격 증명 환경 변수에 `NEXT_PUBLIC_`을 붙이지 않았다.
- [ ] 관리자 API는 기존 관리자 쿠키 인증을 계속 확인한다.
- [ ] ESP32 API는 기존 `X-DEVICE-KEY` 검사를 유지한다.
- [ ] 브라우저 응답이나 오류 메시지에 private key가 포함되지 않는다.
- [ ] 로그에는 학번 전체를 필요 이상으로 남기지 않는다.
- [ ] 유출된 서비스 계정 키를 즉시 비활성화하고 교체할 절차가 있다.

## 12. 테스트 계획

### 12.1 정상 입력

- [ ] 존재하지 않는 `department_id`가 제외된다.
- [ ] 0 미만 또는 999 초과 점수가 제외된다.

- [ ] 오류 행 번호가 관리자 화면에 표시된다.

- [ ] API quota 오류에 제한적인 재시도가 적용된다.

## 13. 단계별 도입 순서

한 번에 양방향 연동을 모두 구현하기보다 다음 순서가 안전하다.

### 1단계: 읽기 전용 연동

- 스프레드시트와 코드표 생성
- 서비스 계정에 뷰어 권한 부여
- `lib/google-sheets.ts`와 파서 작성
- `/api/dashboard`를 시트 기반으로 변경
- 관리자 화면에 동기화 상태 표시

이 단계가 끝나면 운영자가 시트에 직접 입력한 점수가 홈페이지에 자동 반영된다.

### 2단계: 전체 랭킹 조회 전환

- 홈, 게임, 개인, 학과 페이지가 같은 `score-store`를 사용하도록 통합
- 필요한 화면만 polling 적용
- 중복·최고 점수 정책 검증

### 3단계: 양방향 쓰기

- 서비스 계정을 편집자로 변경
- 관리자 직접 입력을 시트 `append`로 변경
- 학생 등록 완료 점수를 시트 `append`로 변경
- 쓰기 성공 후 캐시 무효화
- 중복 요청과 네트워크 재시도 처리

### 4단계: 운영 안정화

- 마지막 정상 데이터 fallback
- 동기화 상태와 오류 행 표시
- 서비스 계정 키 교체 절차 문서화
- 행사 전 부하·네트워크 단절 테스트

## 14. 예상 결과와 제한사항

구현이 완료되면 운영자는 별도의 관리자 폼을 반복해서 사용하지 않고 구글 스프레드시트에서 여러 점수를 붙여넣거나 수정할 수 있다. 홈페이지는 현재 polling 구조를 활용해 보통 수 초 안에 변경된 순위를 표시한다. 서버가 재시작되어도 확정 점수는 시트에서 복원된다.

다만 다음 제한은 남는다.

- 구글 시트 직접 수정은 웹훅이 아니므로 polling 주기만큼 지연된다.
- 시트의 행 순서나 값이 사람이 수정할 수 있는 데이터이므로 강한 검증이 필요하다.
- 대규모 동시 쓰기와 원자적 업데이트는 일반 데이터베이스보다 약하다.
- ESP32의 아직 등록되지 않은 `pending` 세션까지 안전하게 보존하려면 별도 데이터베이스가 필요하다.
- 서비스 계정 인증 또는 인터넷 연결이 실패하면 최신 시트 값을 가져올 수 없다.

행사 규모가 커지면 구글 시트는 운영자가 보는 입력·관리 화면으로 유지하고, 실제 원장은 PostgreSQL에 저장하는 구조로 이전할 수 있다.
